# PCSpeedTest

`bin\PCSpeedTest.exe` — fifteen figures for one machine in one window: the
processor, the memory, the disk, the local network and the internet, each
measured the same way every time and written to a CSV so two runs can be
compared instead of remembered.

Plain C++17 / Win32. No third-party libraries, no installer, no runtime to
ship: the build links the compiler runtime statically, so the executable
depends only on DLLs Windows itself provides.

---

## What it measures

| Group | Row | Unit | How |
|---|---|---|---|
| Processor | CPU - one thread | Mops/s | A dependent integer and floating-point mix, timed for 0.35 s |
| Processor | CPU - every thread | Mops/s | The same loop on every logical processor at once |
| Memory | Memory - copy | GB/s | 64 MiB `memcpy` passes for 0.3 s, after an untimed pass |
| Memory | Memory - latency | ns | A shuffled single-cycle chain of dependent loads over 32 MiB |
| Disk | Disk - write | MB/s | 192 MiB written in 1 MiB blocks, then flushed to the drive |
| Disk | Disk - read | MB/s | The same 192 MiB read back with `FILE_FLAG_NO_BUFFERING` |
| Network | Network - link | Gbps | The adapter carrying the default route, as Windows reports it |
| Network | Network - loopback | MB/s | 32 MiB over a TCP socket on 127.0.0.1 in 64 KiB blocks |
| Network | LAN - latency | ms | Eight ICMP echoes to the default gateway |
| Network | Internet - latency | ms | Ten ICMP echoes to 1.1.1.1, with jitter and loss |
| Network | Internet - download | Mbps | HTTPS GET of up to 40 MiB from `speed.cloudflare.com` |
| Network | Internet - upload | Mbps | HTTPS POST of up to 12 MiB to the same host |
| Graphics | GPU - compute | GFLOP/s | Four independent multiply-add chains on 262144 lanes, dispatched for 0.5 s |
| Graphics | GPU - memory | GB/s | 64 MiB texture copies for 0.5 s, counted as read plus write |
| Graphics | GPU - frames | FPS | A 1080p offscreen scene — 4096 blended quads, depth buffer, cleared every frame — rendered for 0.5 s of GPU time |

`MB/s` and `GB/s` are decimal (10^6 and 10^9 bytes per second); `Gbps` and
`Mbps` are bits per second. The clock is `QueryPerformanceCounter`; the work is
measured, not inferred from a timer alone.

## The window

Fifteen rows in five groups, in the suite's palette. Each row carries what it
measures, how, and the figure as it lands. Click a row to measure just that
row; **Run all** measures the fifteen in catalog order and turns into **Stop**
while a run is in flight, so a long internet test can be abandoned without
closing the window. **Results folder** opens
`%LOCALAPPDATA%\PCSpeedTest\` in Explorer, and **View results** opens the
reader described below.

A metric that cannot be measured says why instead of showing a zero: no reply
to ICMP ("ICMP may be filtered"), no default gateway, a server that answered
with an error, a disk that could not be written. One failure never costs the
other fourteen - the run continues and the CSV simply leaves that column empty.

The window is measured at the monitor's own DPI, scrolls whole rows when there
is more list than window, and carries its own icon (a speedometer on the dark
card, resource id 2) generated by `tools\make_icon.ps1`.

## The CSV

Every completed run of all fifteen appends one line to
`%LOCALAPPDATA%\PCSpeedTest\results.csv`, creating the file and its header on
first use:

```
timestamp_utc,host,cpu,cores,threads,arch,ram_gib,ram_speed,ram_maker,
os,gpu,gpu_driver,gpu_timing,cpu_single_mops,cpu_multi_mops,mem_copy_gbs,
mem_latency_ns,disk_write_mbs,disk_read_mbs,lan_link_gbps,lan_loopback_mbs,
lan_latency_ms,wan_latency_ms,wan_down_mbps,wan_up_mbps,gpu_gflops,
gpu_bandwidth,gpu_fps
```

`cores` is the physical core count and `threads` the logical processor count -
one column called `cores` holding 8 for a four-core processor was a wrong answer
of its own. A file written before that split is rewritten in place on the next
append: the old `cores` figure moves to `threads`, the new `cores` stays empty
for those rows rather than claiming a figure nobody measured, and a row that
said Windows 10 with a build number of 22000 or higher is corrected to Windows
11, because the build in the same row is what decides. `ram_speed`,
`ram_maker`, `gpu` and `gpu_driver` are filled when Windows reports them and
left empty when it will not, so an older row stays readable rather than
invented. `gpu_timing` records which clock produced the three graphics figures:
`timestamp` for the GPU's own timestamp queries, `wall` for elapsed wall time,
`mixed` if a run has both, and empty where no graphics figure was recorded.
Rows written before the column existed migrate with it empty, so a legacy
wall-clock run cannot be mistaken for a timestamped one. The two clocks are not
comparable: a timestamp query measures the work on the GPU and excludes the
gaps where the queue waited for the CPU.

The machine columns are there so readings stay comparable when the file is
copied between machines: a row is the whole context of the run, not just the
numbers. Fields containing a comma or a quote are quoted the way RFC 4180 says,
so the file opens in any spreadsheet without a delimiter question. A metric
that could not be measured leaves its column empty rather than writing a zero,
because zero is a measurement and "unavailable" is not.

Measuring a single row from the window does not write a CSV line - only a
complete run does, so the file never mixes partial rows with full ones.

## Viewing the results

**View results** in the window opens the file as a window of its own, so the
history is readable without a spreadsheet:

- one card per completed run, newest first, carrying the timestamp in UTC, the
  machine name, the processor with its thread count and RAM, and the fifteen
  figures laid out as four columns in catalog order, four to a line;
- a column that could not be measured shows `-` rather than a zero, exactly as
  it is left empty in the file;
- **Open in spreadsheet** hands `results.csv` to whatever application owns
  `.csv` on the machine, **Results folder** opens the folder, and a click on a
  card does the same as the first button;
- the list scrolls a whole card per wheel notch, and Escape or **Close** leaves
  the reader without touching the file;
- **Empty file** removes every run, after a confirmation that names how many go
  and defaults to **No**. What is left is the header alone: the reader reloads
  in place and says there are no runs, and the next run appends to a file that
  still knows its columns. Nothing else in the folder is touched.

The file itself is still the record - the reader only reads it, and picks up a
run made by `--run` in a console the next time it is opened.

## Console modes

```bat
PCSpeedTest.exe                 the window
PCSpeedTest.exe --run           measure all fifteen, print them, append one CSV line
PCSpeedTest.exe --empty         reset results.csv to its header, no window
PCSpeedTest.exe --selftest      prove the engine, print one RESULT: line
```

`--run` is what a scheduled task or a support session uses: it needs no window,
prints one line per metric with its note, and exits 0. `--empty` is the same idea
for the file rather than the machine: it needs no window either, rewrites
`results.csv` with the header alone, prints how many runs went and the path it
emptied, reads the file back to prove the header survived, and exits 1 when the
rewrite fails. It is the console equivalent of the reader's **Empty file**, so a
task can reset the history on a schedule without anything appearing on screen. `--selftest` touches no
network at all and leaves no file behind; it measures the CPU loop, memory
copy and latency, loopback TCP and a 48 MiB disk round trip, checks the units
and the CSV escaping, writes a synthetic results.csv of its own - a quoted host
with a comma in it, a quoted cpu with a quote in it and one blank metric - reads
it back through the same reader the viewer uses, and confirms the machine
description, and migrates a file written under the older header - an old row
kept, its thread count moved out of `cores`, its Windows 10 claim corrected from
its build number, and parses a firmware memory table the test builds itself.
Fourteen checks in about three seconds - the last proves that emptying keeps the
header and loses the runs - and the files it parses
are temporary ones: your `results.csv` is never opened.

## Building

```bat
build_mingw.bat
```

or let the suite do it - `build_all.bat` at the root has this program's recipe
row and builds it with everything else:

```bat
g++ -std=c++17 -O2 -Wall -Wextra -municode -mwindows -static -s ^
    -DUNICODE -D_UNICODE -DWINVER=0x0A00 -D_WIN32_WINNT=0x0A00 ^
    src\pcspeedtest.cpp src\main.cpp -o PCSpeedTest.exe ^
    -lwinhttp -liphlpapi -lws2_32 -ladvapi32 -lshell32 -lole32 -luuid ^
    -lgdi32 -luser32 -ldwmapi -ld3d11 -ld3dcompiler
```

The manifest is `asInvoker`: nothing here needs elevation. Sockets, ICMP
echoes and the program's own `%LOCALAPPDATA%` folder are all a standard user
already has.

## How the machine is described

Three lines under the title, each one the hardware itself rather than a claim
about it: the processor's own name with physical cores over logical threads and
the installed memory (with the modules' speed and maker when Windows reports
them); the adapter the machine draws on and its driver version; then the platform
- the Windows name with edition, version and build, the architecture, and the
adapter carrying the default route with its negotiated speed.

The graphics line comes from `EnumDisplayDevices`, taking the adapter attached
to the desktop, and its driver version from the display class key whose
`DriverDesc` matches that adapter - so a second card in the wrong slot, or a
dongle that is plugged in but not drawing, is not what gets recorded. The memory
figures come from the raw SMBIOS table (`GetSystemFirmwareTable`), type 17 per
module: the configured speed the platform runs it at, and the manufacturer. Two
modules of different makes read as `mixed`, and unequal rates read as a range
(`2666-3200 MT/s`). A machine that refuses the firmware table, or a session with
no adapter of its own, leaves those fields empty rather than filling them in, and
the CSV leaves those columns empty with them.

Windows 11 keeps `ProductName` = `Windows 10 Pro` in the registry for
compatibility, so the version word is taken from the build number instead: 22000
and above is Windows 11, below it is Windows 10, and `Windows Server ...` is
left as the registry names it. Cores come from `RelationProcessorCore`, not from
the thread count, and the architecture from `GetNativeSystemInfo`, so an ARM64
machine is not called x64 by association.

## Notes and limits

- **The internet rows need a network.** Download and upload talk to
  `speed.cloudflare.com`; the latency row pings `1.1.1.1`. A machine behind a
  proxy that blocks either reports that row as unavailable and everything else
  still measures.
- **LAN throughput is loopback, not a second machine.** A real LAN transfer
  needs a peer to send to; the loopback row measures the Windows network stack
  itself, and the link row reports the negotiated speed of the adapter. Both
  together tell you whether a slow transfer is the wire or the machine.
- **Disk figures are for the volume holding `%LOCALAPPDATA%`**, which on most
  machines is the system SSD. The test file is deleted afterwards, including
  when a measurement fails.
- **The graphics rows need a Direct3D 11 device.** Both create one with
  `D3D11CreateDevice` against the hardware driver, compile a compute shader with
  `D3DCompile`, and time their work by queueing an event query and waiting for
  it - the GPU has finished before the clock is read. A session with no adapter
  (a headless VM, some remote desktops) reports that instead of a figure, and the
  compute row's `GFLOP/s` counts a multiply-add as two floating-point
  operations, so it is a ceiling for the shader core, not a game's frame rate.
- **A single run is a snapshot.** Run it two or three times, or chart the CSV,
  before drawing a conclusion about a machine; the point of the file is that
  successive runs are directly comparable.
